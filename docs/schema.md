# Database schema reference

This reference describes the six domain tables and the migration bookkeeping
table created by `src/db/migrate.ts` and `src/db/migrations/`. All fields are
required (`NOT NULL`) unless marked nullable below. `PK` means primary key;
`FK` means foreign key. PostgreSQL creates indexes for primary and unique keys.

## Ownership and accounting rules

- Each user belongs to exactly one account. Accounts and users reference plan
  definitions; their usage is stored separately from those definitions.
- A predefined plan has a null owner. A custom plan belongs to one account.
  Assignments require the correct scope and either a predefined plan or a
  custom plan owned by the receiving account.
- Two users can share Basic or one custom plan while retaining separate usage
  totals. Switching a plan changes its reference without resetting usage.
- Monthly keys are the first day of a UTC calendar month, such as `2026-10-01`.
  A missing subject/month row represents zero usage. Earlier months remain
  separate rows.
- A decision belongs to one account and one of that account's users. The same
  request ID can exist under different accounts, but only once per account.
- An accepted action contributes the same units to its user and account totals.
  Account monthly usage must equal the sum of accepted unique decisions across
  its users for that month; rejected decisions contribute zero units.
- Past decisions retain their original outcome and snapshot when plans change.
  Current assignments and plan limits describe current rules, not past results.

## `accounts`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `id` | `uuid` | PK; generated by the provisioning service. |
| `name` | `text` | Account name; the provisioning service trims it and requires 1–200 characters. |
| `api_key_digest` | `text` | Unique HMAC-SHA-256 digest; the raw API key is never stored. |
| `account_plan_id` | `integer` | FK to `plans.id`; deleting the referenced plan is restricted. |
| `created_at` | `timestamptz` | Defaults to `now()`. |

## `plans`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `id` | `integer` | PK; generated by default from an identity sequence on fresh schemas. Predefined seed IDs are explicitly 1–4. |
| `owner_account_id` | `uuid`, nullable | FK to `accounts.id`; null means predefined. Deleting the referenced owner is restricted. |
| `scope` | `text` | SQL check permits only `account` or `user`. |
| `name` | `text` | Plan name; HTTP custom-plan validation trims it and requires 1–100 characters. |
| `monthly_limit` | `integer` | SQL check: 0–2,147,483,647. |
| `max_units_per_request` | `integer` | SQL check: 0–2,147,483,647. The plan-management API calls this `requestLimit`. |
| `revision` | `integer` | Defaults to 1; SQL check requires a positive value. Successful custom-plan updates increment it. |
| `created_at` | `timestamptz` | Defaults to `now()`. |
| `updated_at` | `timestamptz` | Defaults to `now()`; the custom-plan update service refreshes it. |

The initial migration creates `accounts` before `plans`, then adds the account
plan FK after both tables exist. That resolves their circular references. An
account starts on a predefined plan before it can own custom definitions.

## `users`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `id` | `uuid` | PK; generated by the user service. |
| `account_id` | `uuid` | FK to `accounts.id`; account deletion cascades to its users, subject to other FK restrictions. |
| `user_plan_id` | `integer` | FK to `plans.id`; deleting the referenced plan is restricted. |
| `created_at` | `timestamptz` | Defaults to `now()`. |

The unique key `(account_id, id)` supports account-scoped lookups and is the
target of the composite FKs used by user usage and request decisions.

## `user_monthly_usage`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `account_id` | `uuid` | Part of the composite FK to `users(account_id, id)`. |
| `user_id` | `uuid` | Part of PK and that composite FK; deletion of the referenced user cascades. |
| `usage_month` | `date` | Part of PK; SQL check requires day 1. |
| `consumed_units` | `integer` | Defaults to 0; SQL check: 0–2,147,483,647. |

PK: `(user_id, usage_month)`. The composite FK prevents storing usage under an

## `request_decisions`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `account_id` | `uuid` | Part of PK; FK to `accounts.id` with deletion cascade; also part of the composite user FK. |
| `request_id` | `varchar(128)` | Part of PK; SQL check: 1–128 letters, digits, `.`, `_`, `:`, or `-`. |
| `decision_sequence` | `bigint` | Positive generated-always identity; allocated on insert and used for stable history ordering. Unique within each account through the history index. |
| `user_id` | `uuid` | Composite FK with `account_id` to `users(account_id, id)`; deleting the referenced user is restricted. |
| `requested_units` | `integer` | SQL check: 1–2,147,483,647. Together with `user_id`, preserves canonical payload fields for retry comparison. |
| `processed_at` | `timestamptz` | Defaults to `now()`; processing timestamp. |
| `processed_month` | `date` | SQL check requires day 1; explicit UTC accounting month. |
| `accepted` | `boolean` | Whether the request was accepted. |
| `decision_reason` | `text` | Stored explanation, such as `accepted`. |
| `blocking_rule` | `text`, nullable | Blocking rule; the API contract uses `max_units_per_request` or `monthly_limit`. SQL does not restrict this text. |
| `blocking_scope` | `text`, nullable | SQL check permits `account` or `user` when present. |
| `account_plan_id` | `integer` | FK to `plans.id`; deleting the referenced plan is restricted. |
| `user_plan_id` | `integer` | FK to `plans.id`; deleting the referenced plan is restricted. |
| `account_plan_revision` | `integer` | SQL check requires a positive value; revision at decision time. |
| `user_plan_revision` | `integer` | SQL check requires a positive value; revision at decision time. |
| `decision_snapshot` | `jsonb` | SQL check requires a JSON object; stores the original response/evidence. |

PK: `(account_id, request_id)`. The composite user FK prevents associating an
account's decision with another account's user. A repeated identifier within
one account violates the PK even if a caller bypasses an application lookup.
Neither user nor month is part of that key: a different user or later month
cannot reuse an account's saved ID. Request IDs are case-sensitive. Accepted
and rejected decisions reserve their IDs for the life of the project; there
is no TTL or automatic pruning. Removing the database/volume removes history
and its retry protection.

The schema already provides decision storage. Task 16 defines its public
response shape, Task 17 evaluates quotas, and Task 18 reads, initializes, and
increments explicit UTC monthly buckets. Task 19 inserts decision snapshots and
persists accepted usage in one transaction. Its snapshot contains `response`
(the validated public decision) and `evaluatedLimits` (monthly and per-request
limits for both scopes). Saving these limits and balances preserves the evidence
after mutable plan definitions change. Task 20 wires the production endpoint,
validates snapshots through `src/modules/usage/snapshot.ts`, and verifies them
end to end. The response is serialized from `snapshot.response` after commit;
replay validates that stored snapshot and returns the same historical body.
Snapshots retain their original limits, revisions, balances, and blockers even
when subsequent plan edits or consumption change the live state.

Task 28 exposes the saved response and evaluated limits through authenticated
history pagination. The sequence migration preserves all previous fields,
backfills by processing time/account/request ID, and advances the identity past
the backfill. Tied legacy timestamps receive a deterministic order, not a claim
about their unknown original insertion order. New sequence values are allocated
by the decision INSERT, after the consumption service acquires the account lock.
The application never updates them; identity gaps after rollback are expected.
Continuation cursors preserve an upper sequence bound and move strictly below
the last returned sequence, excluding later insertions for that account.

## `schema_migrations`

| Field | SQL type | Key, default, and meaning |
| --- | --- | --- |
| `version` | `text` | PK; applied SQL filename. |
| `applied_at` | `timestamptz` | Defaults to `now()`. |

The runner creates this table if needed, applies pending files in filename
order, and records each filename in the same transaction as that migration.
Repeating a run skips applied files. The compatibility migration converts older
UUID plan IDs and their references to integers; fresh schemas already use
integer IDs. Older converted schemas use a sequence-backed default for plan IDs.

## Indexes and their queries

| Index or indexed key | Query it supports |
| --- | --- |
| `accounts` PK `(id)` | Account lookup and the account-first `SELECT ... FOR UPDATE` lock. |
| `accounts` unique key `(api_key_digest)` | Authentication lookup by computed digest. |
| `plans` PK `(id)` | Plan inspection, assignment validation, and plan joins. |
| `plans_owner_account_id_idx` on `(owner_account_id)` | Custom-plan catalog visibility and queries for an account's definitions. |
| `users` PK `(id)` | Direct user identity lookup and referenced-key integrity. |
| `users` unique key `(account_id, id)` | Tenant-scoped user lookup, account user lists, and composite ownership references. |
| `account_monthly_usage` PK `(account_id, usage_month)` | A single account's current or historical monthly total. |
| `user_monthly_usage` PK `(user_id, usage_month)` | A single user's current or historical monthly total; service queries must also enforce account ownership. |
| `request_decisions` PK `(account_id, request_id)` | Account-scoped request replay/conflict lookup and duplicate prevention. |
| `request_decisions_account_processed_at_idx` on `(account_id, processed_at DESC)` | Timestamp-based decision inspection; timestamps alone are not the pagination order. |
| `request_decisions_account_sequence_idx` unique on `(account_id, decision_sequence DESC)` | Stable newest-sequence history and cursor range scans for an account. |
| `schema_migrations` PK `(version)` | Applied-migration identity and duplicate prevention. |

Indexes support the stated lookup/order patterns; they do not replace tenant
predicates, ownership checks, or transactions.

## Numeric representation

Quantities use PostgreSQL `integer`, with a supported upper bound of
`2,147,483,647` (`MAX_QUANTITY` in TypeScript). Limits and consumed totals permit
zero; requested units must be positive. `pg` returns SQL `integer` values as
JavaScript numbers, exactly throughout this range, without a custom parser.
SQL `count(*)` returns `bigint`; tests deliberately treat that result as a string.

Decision sequences also use PostgreSQL `bigint`, independently of the unit bound.
History returns them as decimal strings and validates cursor bounds using JS
`BigInt`, preserving values beyond `Number.MAX_SAFE_INTEGER` exactly.

The integration suite writes and reads the lower and upper supported quantity
boundaries through real table columns and checks exact numeric results. It also
verifies that every quantity column rejects `2,147,483,648` with PostgreSQL
numeric-out-of-range error `22003`, rather than silently rounding it.

HTTP validators reject fractions, numeric strings, and out-of-range values
before SQL. The evaluator compares requested units with
`max(0, monthlyLimit - consumed)` before adding, keeping accepted totals within
the supported range. A downgrade can leave consumed usage above a new plan
limit; that usage remains intact and remaining allowance becomes zero.

## Usage reconciliation query

This query checks each stored account bucket against both the sum of its users'
usage and the sum of accepted decision units for the same account and month.
Rejected decisions are excluded. It avoids multiplying rows by summing the two
sources independently. Both match columns should be true once decision storage
is populated alongside usage by the consumption transaction.

```sql
SELECT
  bucket.account_id,
  bucket.usage_month,
  bucket.consumed_units,
  bucket.consumed_units = COALESCE((
    SELECT sum(usage.consumed_units)
    FROM user_monthly_usage AS usage
    WHERE usage.account_id = bucket.account_id
      AND usage.usage_month = bucket.usage_month
  ), 0) AS users_match,
  bucket.consumed_units = COALESCE((
    SELECT sum(decision.requested_units)
    FROM request_decisions AS decision
    WHERE decision.account_id = bucket.account_id
      AND decision.processed_month = bucket.usage_month
      AND decision.accepted
  ), 0) AS decisions_match
FROM account_monthly_usage AS bucket;
```

The Task 18 integration test builds controlled usage and decision fixtures to
prove this check, including another account, another month, and a rejected
decision. It also introduces mismatched user and decision totals to verify
that the query reports failures. These fixtures exercise repository storage;
Task 19 implements the consumption transaction and its rollback checks.

## SQL guarantees and application responsibilities

SQL enforces existence through FKs, account/user consistency through composite
FKs, unique subject/month and account/request keys, valid plan scopes, valid
quantity ranges, and first-day-of-month dates.

Application services enforce plan scope and owner eligibility, read-only
predefined plans, immutable plan scope/owner fields, input string rules, and
account-scoped query predicates. Mutation services lock the account in a
standalone statement before reading mutable plan data in subsequent statements,
then commit or roll back together and release the checked-out connection.

The consumption service coordinates both usage totals and decision persistence,
builds accepted/rejected metadata from the evaluator, selects the UTC month from
post-lock processing time, and only inserts decision history. SQL currently
checks only that snapshots are JSON objects;
there is no trigger validating their response shape or preventing all direct SQL
updates. Plan changes preserve usage and historical decisions through the
application's update paths. There are no public account, user, plan, or history
deletion endpoints.
